# GST Gaming Prioritisation Framework

A single-page HTML app (`index.html`) for the Gaming Super Tribe prioritisation framework, hosted on GitHub Pages at https://georgechilcottuki.github.io/gst-prioritisation/

The app connects to a SharePoint List called "GST Prioritisation" on betfairprod.sharepoint.com/sites/gamingsupertribelt via Microsoft Graph API (MSAL OAuth). localStorage is used as a fallback.

Key files:
- `index.html` — the entire app (HTML + CSS + JS, self-contained)
- `.nojekyll` — empty marker file telling GitHub Pages to skip Jekyll processing. This is a plain static site with no Jekyll dependency; don't remove this file.

Deployment: push to `main` → GitHub Pages auto-deploys via Actions.

## Lessons learned
- CSV import: text labels use en-dashes (–) not hyphens (-) in score maps — normalise with normStr() before lookup
- SharePoint items arrive with all numeric scores = 0; always run resolveScores() before hasTBC()
- Empty commercial/bizrisk fields from CSV = N/A (score 1), not TBC (score 0)
- Brand field can contain non-brand text from CSV — defaults to All (score 2) if unrecognised
- MSAL v3 requires initialize() before handleRedirectPromise()
- isWip must be explicitly set on item before saving to SharePoint
- Literal newlines inside JS string literals break the entire script — use \\n not a real newline
- hasTBC() must call resolveScores() first so SP items with score=0 but valid text are handled correctly
- setStatus() and showSignInButton() must be defined before the Graph module calls them — place at top of script
- CSV row joins must use a real newline escape `'\n'`, not the two-character literal `'\\n'` — the latter compiles fine but produces backslash-n text instead of a line break, so the exported file renders as one line. saveBackupToSP() had the correct form; exportCSV() didn't.
- The priority score formula is `(brand+invest+urgency+mission+vsMetric+impact+commercial+risk) * (urgency+reason) / effort` — `impact` must be included. calc() (Add-form live preview) and parseImportCSV() both omitted it, so the live preview and CSV-imported items diverged from the score actually saved. Always check new/changed score-calculating code against calcScore() (the canonical implementation) for the full field list.
- fetch() only rejects on network failure, not on HTTP error status (4xx/5xx) — every write to Graph (spSaveItem, spDeleteItem) must explicitly check `response.ok` and throw, otherwise a rejected write (auth expired, bad field, etc.) is silently treated as a successful save.
- resolveSiteAndList() is called from many places (spSaveItem, spDeleteItem, initMSAL) and only guarded re-entry via `if (_siteId && _listId)`, so concurrent callers before the first resolve completes would each fire duplicate Graph lookups. Fixed with a `_resolvePending` queue: the first caller starts the fetch, later concurrent callers are queued and all fire once the in-flight resolve finishes.
- The priority formula now lives in exactly one place: `computePriority(brand,invest,urg,mm,vs,impact,comm,risk,reason,effort)`, defined just above calcScore(). Every score-calculating call site (calc(), addInitiative(), editCalc(), saveDetail(), parseImportCSV(), repairAll() via calcScore()) must call it rather than inlining the formula — inlining it separately is what caused `impact` to silently go missing from two call sites before. If the formula ever needs to change, it should only need to change here.
- The Add-form "Live score" breakdown panel was missing a "Reason" cell even though Reason is a real scoring input included in the formula — it was tracked in calc()'s anyTBC check but never rendered. When adding/removing a scoring field, check both the calculation (computePriority call sites) AND the score-panel HTML/calc() DOM updates — they're two separate things that can each drift independently.
- CSV import now reviews for duplicates before writing anything. `parseImportCSV()` matches each row's initiative name (via `findBacklogMatchByName()`, normalised comparison against the current backlog+WIP) and also against earlier rows already seen in the same file. Each row is tagged `_dupType` (null | 'existing' | 'batch'), `_dupId`, `_dupName`, `_include` (default true for new rows, false for duplicates). The import modal shows two checklists — "New items" and "Possible duplicates" — with per-row and select-all/none toggles; nothing is written to `initiatives`/SharePoint until the user clicks "Apply".
- IMPORTANT: checked duplicate rows in the import review are added as new, independent items — same as new rows — not merged into the existing matching item. An earlier version tried to "smart merge" checked `_dupType==='existing'` rows into the matching backlog item in place; this looked like a bug ("checking a duplicate does nothing") whenever the CSV data matched what was already stored, since the merge produced no visible change. `confirmImport()` just strips the `_dup*`/`_include` fields and pushes every checked row via `initiatives.push()`, exactly like a plain new item. If a "sync latest data into an existing item via CSV" feature is wanted later, it needs to be a clearly separate, explicit action — not the default behaviour of checking a duplicate.
- `dateAdded` is now a `dd/mm/yy hh:mm:ss` timestamp via `nowStamp()` (defined near the other small helpers, esc/vv/tt/sel), not just a date, so it's possible to tell exactly when an item was added, not just the day. Set at creation time in `addInitiative()` and `parseImportCSV()` only — never touched on edit/save, so it reflects when the item first entered the backlog. Visible in the initiative detail modal and in CSV exports; no dedicated backlog-table column for it yet.
- `dateAdded` is a free-format string, not something ever parsed back into a Date — CSV export/import and the detail modal just pass it through and quote/escape it like any other text column, so changing its format (date-only vs dd/mm/yy hh:mm:ss) never risks breaking export/import. Old items created before a format change simply keep their old string until edited.
- Both exportCSV() and saveBackupToSP() build a filename timestamp — previously duplicated inline in each. Consolidated into `fileTimestamp()` (next to `nowStamp()`): a filesystem-safe `YYYY-MM-DD_HHMMSS` stamp (no slashes/colons, seconds precision) so repeat exports/backups in the same session get distinct filenames instead of overwriting.
- Favicon is a `<link rel="icon" type="image/svg+xml" href="data:image/svg+xml;base64,...">` in `<head>`, not a separate file — keeps the app a single self-contained HTML file. It's a small blue-accent (#1a56db) ascending-bars icon. To change it, re-encode a new SVG to base64 and replace the href; don't add a physical favicon.ico/svg file to the repo.
- IMPORTANT — CRITICAL BUG (fixed): editing an existing item never actually persisted to SharePoint, even though it looked like it worked (local UI updated, no error shown) — a refresh would silently revert it back to the stale SharePoint value. Two separate bugs combined to cause this — both had to be fixed:
  1. spSaveItem()'s update branch PATCHed `/sites/{s}/lists/{l}/items/{id}` (the item resource) with a `{"fields": {...}}`-wrapped body. Graph accepts that request and returns 200 OK, but that endpoint doesn't actually persist column values — updates must PATCH `/items/{id}/fields` directly with the raw fields object (no wrapper). Verified against Microsoft's official listItem-update docs. Fixed via `listItemFieldsUrl()`.
  2. saveDetail()'s final branch (editing an existing, already-fully-scored, non-WIP item — i.e. ordinary edits like changing Status) called bare `save()` instead of `saveItem(it)`. `save()` only writes to localStorage; `saveItem(it)` does that AND calls `spSaveItem(it)`. This meant ordinary edits never even attempted a network call to SharePoint at all — confirmed via the Network tab showing zero requests on save. This was the actual root cause of the reported symptom; bug #1 was real and worth fixing but wasn't what was causing this specific report, since the buggy code path never got as far as making the fetch call in the first place.
  Lesson: when SharePoint writes don't stick, check the *call site* (does this code path call `saveItem()`/`spSaveItem()` at all?) before assuming the problem is inside `spSaveItem()`/Graph itself. Every `save()` call in the codebase that ISN'T immediately followed by its own explicit `spSaveItem()`/`spDeleteItem()` loop is a bug — grep for `save()` vs `saveItem(` to audit.
- saveBackupToSP() (fires before delete/clear-all, uploads a CSV snapshot to the SharePoint `GST-Backups` folder) had three silent-failure paths — not connected yet (`!spReady || !_siteId`), no token, and the upload PUT itself failing (non-ok response or thrown error) — that each only did `console.error`/nothing and let the delete proceed anyway with zero user-facing indication. If backups stop appearing, this is why: nothing before this fix would ever have told the user. All three paths now `showToast()` a warning. Deletion still proceeds either way — this wasn't changed to block on backup failure, just to surface it; worth revisiting if silent data loss on delete becomes a real concern.
- "Clear all" was renamed to "Delete all" throughout — button label, modal (`clear-modal` → `delete-all-modal`), and functions (`askClearAll`/`confirmClearAll` → `askDeleteAll`/`confirmDeleteAll`) — with a stronger red "this cannot be undone" warning banner in the confirmation modal (previously a plain `<p>`). The `saveBackupToSP('clear-all', ...)` reason string passed internally was deliberately left as `'clear-all'` (not renamed to match) so backup filenames stay consistent with older backups already using that tag — it's an internal filename tag, not user-facing.
- Added a "Live" tab for initiatives whose status is "in flight/live" (originally status 11–13, now just the single status "Measure" — see status migration entry below), so the Backlog only shows work still to be done. Implemented as a **display-time filter** via `isLiveStatus(status)` — there is deliberately NO separate `liveInitiatives` array and NO new SharePoint field. Live items stay in the same `initiatives` array (`isWip` still `false`); `renderBacklog()`/`renderLive()` just filter it two different ways. This was a deliberate choice over adding a new persisted bucket (like WIP has) specifically to avoid opening a new SharePoint schema/sync surface after the session spent fixing several Graph API sync bugs — an item moves between Backlog and Live the instant its Status field changes, with no explicit "move" action or extra SharePoint column needed.
  - Consequence to remember: anywhere that mutates or bulk-clears `initiatives` must account for Live items sharing the array. `confirmDeleteAll()` was fixed to only delete non-live items when triggered from the Backlog tab (`initiatives.filter(i => !isLiveStatus(i.status))`), preserving Live items — the naive `initiatives=[]` from before this feature would have wiped Live items too.
  - Every function that calls `renderBacklog()`/`renderWIP()` to refresh the UI after a data change should also call `renderLive()` — audited and fixed all call sites (add, edit/saveDetail, delete, delete-all, CSV import, repair, move-to-backlog, initial load/refresh). If a future change adds a new `initiatives`-mutating flow, remember to call `renderLive()` there too, and to re-check `updateCount()`'s two badges (`count-badge` excludes live, `live-count-badge` includes only live).
  - `saveDetail()` and `addInitiative()` route to the Live tab (`showTab('live')`) instead of Backlog when the saved item's status resolves to a live status, so the user lands where the item actually ended up.
- Status dropdown reduced from 15 numbered values ("00. Not started" ... "14. Paused") to 8 plain values (Not started, Needs Tech Enabler, Ideate, Validate, Plan, Build, Measure, Paused). `isLiveStatus()` now just checks `s === 'Measure'` (no more numeric prefix/regex). Full old→new mapping lives in `STATUS_MIGRATION_MAP`; see the map itself for the exact 15→8 mapping rather than duplicating it here.
  - Migration is a **display-time mapping**, same pattern as the Live tab filter: `migrateStatus()`/`migrateStatuses()` are called wherever status is first read from external data — `graphToItem()` (SharePoint), all three `load()`/`loadLocalFallback()` definitions (localStorage), and `parseImportCSV()` (CSV import). There is no separate one-off migration script; every load path re-applies the mapping, so old-format data anywhere always displays correctly in the app regardless of what's actually still stored.
  - IMPORTANT: this does NOT automatically rewrite the old-format value sitting in SharePoint itself — that only happens when an individual item is next saved (edit+save calls `saveItem()`, which persists whatever `.status` is currently in memory, i.e. the already-migrated value). To push the migrated status back into SharePoint for every item at once (so the raw SharePoint list also shows the new values, not just this app), click "Repair scores" (`repairAll()`) once after this deploys — it already re-saves every item, and since migration has already run by the time it does, that push carries the new status values too. `statusBadge()` was also rewritten to exact-match the new 8 values instead of substring-matching the old label text — it assumes migration has already run (which it always will have, since every load path applies it before anything renders).
- WIP table now shows a Product Prioritisation column, via `hasProductPriorityInputs(it)` (same field list as `hasTBC()` minus `effortScore` — Product Priority's formula never uses Effort, only `priority` = productPriority/effort does). If every non-effort field is resolved, `renderWIP()` computes and shows the real score (passing `it.effortScore||1` into `computePriority()` since we only read `.productPriority` off the result, which doesn't depend on the divisor); otherwise shows '—'. WIP rows are sorted by this value descending (items with no score sort last), specifically so the highest-value WIP items surface first when deciding what to size up for effort next. Deliberately doesn't reuse/mutate `it.productPriority` — computed fresh into a local `{it, pp}` wrapper array each render, so nothing WIP-specific leaks into the persisted item object.
- Backlog/WIP/Live tables' column widths are meant to line up 1:1 by position — e.g. Backlog's 9th column (`min-width:90px`) should match whatever sits in the 9th column of the other two tables, even though the column's *content* differs per table (Prioritised by effort / TBC fields / Prioritised by effort). If a future column is added/reordered in one table, check the other two for the same position rather than assuming widths carry over automatically — they don't share a stylesheet rule, each `<th>` sets its own width inline.
- Tribe "Community" renamed to "Community & FTP" — same pattern as the status rename: `migrateTribe()`/`migrateTribes()` (right next to `migrateStatus()`/`migrateStatuses()`) applied at the same 5 load points (`graphToItem()`, all three `load()`/`loadLocalFallback()` definitions, `parseImportCSV()`). Same caveat as status migration applies: this is display-time only, it doesn't rewrite the old value sitting in SharePoint until that item is next saved (or "Repair scores" is clicked, which re-saves everything). When renaming any other fixed dropdown value (tribe, brand, investment type, etc.) in future, follow this same pattern — dropdown option text + a `migrateX()`/`migrateXs()` pair wired into the same 5 load points — rather than only updating the dropdown, which would leave existing data mismatched against the new option list (breaking exact-match filters).
- Added a "Progress update" free-text field, `it.progressUpdate` — SharePoint column `ProgressUpdate` was created (internal name exactly `ProgressUpdate`, no space, "Multiple lines of text"/plain text) and confirmed syncing correctly. No history is kept; each save overwrites the value for that item. Not a mandatory field — it's not part of `hasTBC()`'s field list, so leaving it empty never affects TBC/WIP status.
  - Editing is only via the full Edit form (`edit-progress-update`, a plain textarea sitting right next to `edit-comments`), saved via the normal "Save changes" button (`saveDetail()`) alongside every other field — no standalone save path of its own (an earlier version made it independently editable straight from the view/preview mode via its own Save button; that was deliberately reverted).
  - In view/preview mode it's a dedicated full-width block (own labeled `<div>`, not part of the 2-column `detail-meta` grid) sitting directly beneath the Comments block, matching how it's `grid-column:span 2` (full width) in the edit form — it was briefly folded into the `detail-meta` grid as a same-size box like Brand/Sponsor, but that read awkwardly for a potentially-long free-text field, so it got its own full-width row instead. Always visible with an em-dash fallback when empty (unlike Comments, which hides entirely when empty). Set via `.textContent` (`it.progressUpdate||'—'`), not `.innerHTML`, so no `esc()` call is needed and there's no risk of the `esc(undefined)` → literal `"undefined"` bug that an earlier `innerHTML`-based version had.
  - Wired into `itemToGraph()`/`graphToItem()` as SharePoint field `ProgressUpdate`, and into CSV export/import (`saveBackupToSP()`, `exportCSV()`, `parseImportCSV()`'s colMap) for round-trip consistency with other free-text fields.
